# Offer、MVP 与交付

## 从技能到结果承诺

技能不是产品。用以下结构封装 offer：

```text
为【客户】在【场景/期限】解决【核心问题】，
通过【机制与交付】达到【可观察结果】，
包含【范围】，不包含【边界】，由【证据】支持。
```

没有证据时，把结果写成待验证假设，避免收益保证或绝对承诺。

## 选择产品形态

| 问题特征 | 优先形态 | 主要风险 |
|---|---|---|
| 高度个性化、问题尚未摸清 | 诊断、咨询、代做/陪跑 | 时间上限、范围失控 |
| 方法稳定、结果可标准化 | 模板、工具包、课程、轻服务 | 用户只买不使用 |
| 需要练习、反馈、监督 | 训练营、社群、周期服务 | 运营强度和情绪劳动 |
| 高频重复、规则稳定 | 软件、自动化或订阅 | 开发过早、维护成本 |
| 高风险或强专业责任 | 人工服务+专业复核 | 合规、责任和资质 |

初期不是默认做低价数字产品。若缺流量和信任，高接触服务可能更快获得客户语言、交付证据和案例；当重复模式稳定后再资产化。

## MVP 设计

MVP 是“能解决核心问题并产生学习的最小完整交付”，不是残缺品。

固定步骤：

1. 只选择一个客户、场景、问题和主要结果。
2. 写明本轮最重要的未知：问题、承诺、价格、渠道或交付，只优先验证一个。
3. 选择最低成本的真实交付：文档、表格、语音、直播、咨询、手工服务或原型均可。
4. 预先写成功信号、护栏、最大投入和停止条件。
5. 从真实目标用户中招募最小但足以支持本轮决策的样本；不硬套统一人数。
6. 交付并记录行为、结果、返工、工时、退款、原话和例外。
7. 一轮只改一个关键变量，决定 `scale / iterate / stop`。

## 验证对象

同时检查：

- 问题验证：是否真实且优先？
- 承诺验证：用户是否理解并重视结果？
- 付费验证：付款是否真实，价格是否影响客户质量？
- 交付验证：能否在范围内产生结果？
- 经济验证：扣除直接成本和工时后是否可持续？
- 创始人验证：这种客户和交付是否符合生活边界？

免费试用只能验证部分使用行为。需要验证商业价值时，应设计真实付款、定金或其他足够强的承诺信号。

## 交付 SOP

记录：准入条件 → 诊断 → 目标确认 → 交付步骤 → 客户责任 → 接触点 → 验收 → 反馈 → 售后 → 退出。把标准流程和例外分开，避免把每单定制误认为产品。

先保证承诺结果、诚信、安全和售后，再追求自动化。只有重复出现且能清楚验收的部分才进入模板、脚本、AI 或外包。

## 停止与调整

- 有问题但 offer 不被理解：调整表达或范围。
- 有兴趣但无强行为：检查优先级、信任、风险和客户选择。
- 有付费但无结果：停止放量，修交付或承诺。
- 有结果但亏损/过载：调整范围、价格、形态或客户。
- 多轮低成本验证仍没有深层行为：停止或迁移，不用更多内容掩盖。

输出 Offer 卡、MVP 实验卡、交付 SOP、证据账本和继续/调整/停止结论。
