# 产品形态分支执行手册

## 分支选择原则

产品形态不是从偏好或“更容易规模化”出发，而由问题个性化程度、方法稳定性、反馈要求、使用频率、输入结构、责任风险和已验证证据决定。验证期原则上只运行一个核心 Offer；分支可以迭代，但不能同时开发四种完整产品。

```text
高度个性化、问题仍在学习 → 产品化咨询
方法稳定、需要练习反馈 → 课程或训练型产品
用户需要持续查询和套用 → 产品知识库
任务高频、规则稳定、输入输出可结构化 → Web 应用
```

课程、产品知识库和 Web 应用都应继承人工咨询/交付中已经验证的客户语言、流程、结果和例外，而不是替代付费与交付验证。

## 产品化咨询

### 进入条件

- 客户问题真实且优先，但不同客户的上下文和方案差异仍大。
- 价值主要来自诊断、判断、取舍、关系和个性化方案。
- 用户能够限定范围、容量、沟通方式和不承诺结果。

### 必备产物

- 咨询 Offer 卡、客户准入/拒绝条件。
- 事前问卷、资料清单和诊断框架。
- 服务范围、客户责任、接触点、修改次数、售后和退出机制。
- 交付模板、结果验收、工时/成本记录和异常升级。
- 客户反馈、结果证据和案例授权记录。

### 内测/交付闸门

至少完成真实交付并记录结果、返工、例外、工时和客户体验；样本数量依据本轮决策，不硬编码。客户满意表达不能替代结果证据。

### 调整或停止

- 范围持续失控：缩小客户/问题或重写责任边界。
- 有结果但过载：提高标准化、调整价格/范围或限制容量。
- 有付费无结果：停止招募，修承诺和交付。
- 问题和流程开始重复：将稳定部分转入课程、产品知识库或工具，保留高判断环节为咨询。

## 课程

### 进入条件

- 不同客户反复出现相同问题，解决步骤和关键练习开始稳定。
- 学员可以通过学习、练习、反馈或监督取得可观察进展。
- 课程所需的案例、练习、反馈标准和常见误区来自真实交付，而非只来自文章目录。

### 必备产物

- 目标学员、进入基线、学习结果和不适用人群。
- 课程结果—模块—练习—反馈—验收映射。
- 最小内测课程，不先制作全部高清录播和完整平台。
- 作业、评分/反馈标准、答疑边界、完成和退出机制。
- 内测招募、学习行为、完成情况、结果、退款和访谈记录。
- 版本改动和内容更新责任。

### 内测闸门

用户完成关键练习并出现与学习目标对应的可观察进展；交付成本、反馈强度和答疑边界可持续。购买、报名或观看不能单独证明课程有效。

### 调整或停止

- 买而不用：检查目标、使用场景、任务负担和反馈机制，不先增加内容。
- 完成但无结果：修学习设计、练习或承诺。
- 结果依赖大量个性化判断：回到咨询/陪跑，不强行录播化。
- 多轮内测仍无法产生进展：停止或重构问题和目标学员。

## 产品知识库

### 固定边界

产品知识库是面向客户的交付产品或持续服务，不是只读源知识库。只能写当前工作区的产品目录；若配置了 `DUGUJUN_KNOWLEDGE_BASE_ROOT`，不得在源知识库下创建、改写、移动或删除文件。

### 进入条件

- 用户需要反复查询、比较、套用模板或做决策，而非只阅读一次。
- 已有稳定知识单元、使用场景、客户语言、模板和案例边界。
- 更新频率、维护责任、权限、来源和版本可被治理。

### 必备产物

- 用户任务和检索场景清单。
- 信息架构、知识单元规范、标签/导航和入口设计。
- 内容来源、事实/观点/外部主张、更新时间和授权记录。
- 模板、案例、快速路径、失败路径和使用说明。
- 搜索/导航/套用测试、更新节奏、版本日志和下架规则。
- 产品承诺、访问方式、售后和数据/权限边界。

### 内测闸门

目标用户能在真实任务中找到正确内容、理解边界并完成预期动作；维护成本和更新责任可接受。文件数量、页面数量和内容完整度不能替代任务成功。

### 调整或停止

- 找不到：修信息架构、标签和入口，不只增加内容。
- 找到但不会用：增加任务路径、模板、示例和验收。
- 高频需要人工解释：转为课程/咨询，或只把稳定部分留在知识库。
- 外部信息快速过期且无维护能力：缩小承诺、增加时效标记或停止对应模块。

## Web 应用

### 进入条件

以下条件缺一时优先用表格、文档、人工服务或无代码原型补证：

- 用户需要高频重复完成同一项任务。
- 输入可以结构化，核心规则稳定，输出可明确验收。
- 人工/半人工版本已反复产生结果，并记录了常见例外。
- 软件相比文档、咨询或产品知识库能显著降低摩擦或提高结果稳定性。
- 用户愿意持续使用或付费，维护、安全和数据责任可接受。

### 必备产物

- 用户任务、使用场景、现有替代和问题证据。
- PRD：用户、任务、输入、处理、输出、边界和非目标。
- 数据字典、权限、隐私、安全、日志和删除/导出规则。
- 低成本原型、可用性测试、失败路径和人工回退。
- MVP 功能清单、验收测试、监控、支持和版本计划。
- 开发/维护成本、使用频率、付费和留存假设。

### 原型闸门

目标用户能完成核心任务，输入输出稳定，主要例外有人工处理路径，用户行为证明软件形态减少了真实摩擦。对原型表示喜欢不能替代使用和结果证据。

### 开发与上线闸门

开发只覆盖已验证的核心路径。自动化、付费、敏感数据、公开部署和账号权限必须有人工验收、失败保底和回滚。公开部署属于外部动作，必须明确批准并核验上线状态。

### 调整或停止

- 低频使用：回到产品知识库、模板或咨询。
- 规则频繁变化：维持人工/半人工，不扩大开发。
- 结果依赖创始人判断：把判断点保留人工，不伪装成全自动。
- 维护、安全或获客成本超过价值：缩小功能、调整模式或停止。

## 分支迁移

分支不是不可逆选择。迁移必须写明旧分支证据、迁移原因、保留资产、失效承诺和需要重新验证的假设。

常见迁移：

- 咨询 → 课程：重复问题、练习和反馈标准稳定。
- 咨询 → 产品知识库：用户持续复用模板、案例和决策材料。
- 咨询/知识库 → Web 应用：任务高频、规则和输入输出稳定。
- 课程 → 咨询：结果高度依赖个别情境和判断。
- Web 应用 → 知识库/服务：使用频率不足、规则不稳或维护成本过高。

已有成交、结果和满意度只能支持原版本、原客户和原场景；产品形态变化后必须重新验证使用、结果、经济性和风险。

## 分支完成条件

一个分支可以标为阶段完成，但不因此宣告商业闭环已经规模化。至少检查：目标客户、问题、承诺、真实使用、结果、经济性、维护/交付容量、退款/投诉、风险和生活边界。证据不足时保持 `validation` 或 `systemization`，不得因产品已做完而升级成熟度。
