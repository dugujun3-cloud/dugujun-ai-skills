# 数据基础、建模与测量

用于回答“用户数据怎么打通、埋点如何设计、CRM/CDP 怎么选、指标为什么对不上、预测模型能不能用于运营、渠道或活动如何归因、怎样验证增量”。本模块将数据与模型限定为决策工具，不把系统采购、相关性或预测分数包装成业务结果。

## 1. 适用问题与边界

适用于：

- OneID、账户—设备—会员—企业身份映射与去重口径。
- 事件、埋点、属性、指标字典、数据质量和权限设计。
- CRM、SCRM、CDP、数据仓库和营销自动化之间的职责划分。
- 漏斗、Cohort、渠道/活动归因、随机实验和准实验设计。
- 流失、响应、倾向、LTV、推荐、聚类等模型的业务评估与上线边界。
- 数据缺失、重复、延迟、污染、漂移和结论等级判断。

不直接替代：

- 数据库、埋点 SDK、实时计算、特征平台和模型服务的工程开发。
- 法务、信息安全、隐私影响评估和供应商安全审查。
- 在没有数据和验证集时训练模型或生成预测结果。
- 在没有合格反事实时证明因果或增量。

## 2. 最少输入

| 输入 | 最低要求 |
|---|---|
| 决策问题 | 要支持哪个运营决策，谁在何时采取什么动作 |
| 业务对象 | 个人、家庭、账户、设备、企业、门店、订单或其他实体 |
| 用户旅程 | 关键状态、事件顺序、目标行为和观察窗口 |
| 数据源 | 事件、交易、权益、服务、渠道、活动、企业或反馈数据来源 |
| 标识 | 匿名主键、来源标识、可否映射、有效期和冲突规则 |
| 口径 | 指标分子、分母、时间、去重和归属规则 |
| 数据质量 | 覆盖、重复、缺失、延迟、回补、异常和版本信息 |
| 验证条件 | 基线、对照、标签成熟度、训练/验证窗口或实验条件 |
| 权限约束 | 采集目的、同意、访问、保留、删除和审计要求 |

不得为分析方便索取姓名、手机号、邮箱、身份证、OpenID 或完整地址。优先使用匿名 ID；如身份映射确需直接标识，由用户在其合规环境内完成，只提供字段规范和检查方法。

## 3. 诊断步骤

### 3.1 从决策倒推数据

按以下顺序建设，避免“先买系统再找场景”：

```text
业务决策 → 运营动作 → 目标人群 → 关键状态/行为 → 指标
→ 事件与实体 → 数据源 → 身份映射 → 质量与权限 → 验证方法
```

每个字段必须说明会改变哪个决策。没有明确使用者、动作和停用规则的字段不进入首期建设。

### 3.2 建立实体与 OneID 规则

先区分实体：用户、账户、家庭、设备、企业、联系人、门店、订单和权益不是同一对象。OneID 是可审计的映射规则，不是“把所有表连起来”。

| 字段 | 要求 |
|---|---|
| 主实体 | 决策按谁去重和归属 |
| 来源标识 | 每个系统中的匿名标识和生成方式 |
| 映射证据 | 登录、经授权绑定、确定性业务关系或概率推断 |
| 置信等级 | 确定、待确认、概率关联、冲突 |
| 生效区间 | 开始、失效和历史回看规则 |
| 冲突处理 | 一对多、多对一、共享设备、换号、解绑和合并撤销 |
| 审计 | 规则版本、来源、负责人和回滚记录 |

判断规则：

- 确定性且有合法业务依据的映射优先；概率映射不得覆盖原始标识。
- 共享设备、家庭账户和企业多人账户不能自动合并为一个人。
- 合并必须可追溯、可撤销；冲突数据保留原始来源。
- 同一分析可同时保留“账户级”和“用户级”口径，不能静默切换。

### 3.3 设计事件与埋点

事件字典至少包括：

| 事件 | 业务含义 | 触发条件 | 主体 | 对象 | 必要属性 | 时间 | 去重键 | 来源 | 版本 | 负责人 |
|---|---|---|---|---|---|---|---|---|---|---|

事件只记录已发生的可观察事实。不要把“高意向”“已激活”“高价值”作为原始事件；它们应由明确规则或模型计算，并保留版本。

埋点检查顺序：

1. 事件是否对应一个真实、可重复识别的行为。
2. 客户端、服务端和第三方来源谁是权威源。
3. 事件时间、入库时间、时区和迟到回补如何处理。
4. 重试、刷新、跨端、离线、取消和退款是否会重复或反转。
5. 属性是否稳定、枚举是否有字典、空值是否有业务含义。
6. 版本变更是否会破坏历史可比性。

### 3.4 划分 CRM、CDP 与数据仓库职责

不要按厂商品牌名称判断，按能力和责任判断：

| 能力层 | 主要职责 | 不应默认承担 |
|---|---|---|
| 业务系统/交易系统 | 账户、订单、权益、履约等业务事实 | 全域身份和任意分析 |
| 数据仓库/湖仓 | 汇总、清洗、历史、指标与分析数据 | 一线客户跟进流程 |
| CDP/用户数据层 | 合法授权范围内的身份、标签、人群和激活 | 替代源系统或自动证明增长 |
| CRM/SCRM | 线索、客户、联系人、跟进、服务和关系记录 | 成为未经治理的全量事实源 |
| 营销自动化 | 基于事件和规则执行旅程 | 自行决定人群、频控和合规边界 |
| BI/实验平台 | 监控、分析、实验与决策呈现 | 修复错误源数据 |

选型前写清：必需场景、数据量与延迟、身份范围、权限、接口、日志、可导出、供应商锁定、总成本、上线依赖和退出方案。没有场景验证时不建议一次建设全量系统。

### 3.5 做数据质量审计

| 维度 | 检查问题 | 失败影响 |
|---|---|---|
| 完整性 | 关键人群、渠道和事件是否覆盖 | 结论只代表可见部分 |
| 唯一性 | 用户、订单和事件是否重复 | 人数与转化虚高 |
| 一致性 | 跨系统定义、时区、状态是否一致 | 指标互相矛盾 |
| 准确性 | 事件是否符合业务事实 | 错误定位卡点 |
| 时效性 | 延迟和成熟窗口是否可接受 | 过早决策 |
| 可追溯性 | 来源、版本、处理和负责人是否可查 | 无法复现和审计 |
| 稳定性 | 近期变更、断点和分布漂移是否监控 | 趋势不再可比 |

先量化质量问题影响哪些人群、指标和时间，再决定修复、降级使用或停止分析。

### 3.6 判断是否需要模型

按最低复杂度选择：

1. **描述性规则**：清晰阈值即可支持动作时优先使用。
2. **评分或分层**：多个稳定信号需组合，但可解释规则足够。
3. **预测模型**：需要估计未来事件概率，且有成熟标签、特征和验证窗口。
4. **增量/uplift 模型**：需要识别“因干预才改变”的人群，且有随机或可信干预数据。
5. **推荐/排序模型**：候选规模大且有明确效用、反馈和探索机制。

只有响应倾向模型时，不能推断“发券后会多买”；高响应用户可能本来就会购买。需要增量决策时优先实验，或使用有干预标签的增量模型。

### 3.7 检查模型全生命周期

```text
业务决策 → 标签定义 → 样本与成熟窗口 → 特征可用时点
→ 训练/验证/时间外测试 → 业务阈值 → 干预 → 实验验证
→ 线上监控 → 漂移/公平/成本 → 复训或下线
```

必须排查：

- 标签泄漏：预测时不可获得的结果字段进入特征。
- 时间穿越：训练、验证和特征窗口晚于决策时点。
- 选择偏差：只用已触达、已购买或可观测用户训练却外推全量。
- 类别不平衡：只报准确率而忽略召回、精确率、校准和业务成本。
- 阈值任意：按“前若干名”触达却没有预算、容量和误伤成本依据。
- 漂移：用户、渠道、产品、价格、事件或策略变化后模型仍照常使用。

低频或机会驱动业务还要处理时间问题：

- 不把“固定自然月未发生交易”直接当流失标签；先定义需求机会、成熟窗口和业务可观察终点。
- 未观察到结果可能是右删失，不自动记为负样本；用户退出、合同到期、竞争事件等可能构成不同风险结局。
- 交易间隔、季节、品类和个人历史周期可以作为候选信号，但必须只使用决策时点前已知信息。
- 可用生存/风险模型比较“何时发生”，但仍需检查时间外校准、删失假设和行动价值；复杂模型不自动优于机会规则。

### 3.8 选择归因与验证方法

| 决策强度 | 优先方法 | 能回答什么 | 主要限制 |
|---|---|---|---|
| 监控 | 描述性漏斗/Cohort | 发生了什么 | 不能解释原因 |
| 运营归属 | 规则归因、多触点报告 | 按约定把结果记给谁 | 不等于增量贡献 |
| 因果验证 | 随机对照、长期保留组 | 干预是否造成变化 | 需要分流、样本和污染控制 |
| 条件受限 | 时间/地域切换、差分、匹配或其他准实验 | 在假设成立时估计影响 | 对可比性和同期变化敏感 |
| 预测 | 时间外验证的模型 | 谁更可能发生结果 | 不证明干预效果 |

归因规则必须说明触点范围、窗口、优先级、跨端、自然流量、重复转化、退款回冲和版本。多触点归因模型不能替代随机实验。

存在社交传播、同群触达、门店/地域共享供给或平台网络效应时，用户级随机可能相互污染。按干扰来源选择：

- 以账户、社群、门店、地域或最小市场为簇随机，并报告簇数、簇内相关和有效样本损失。
- 对时段敏感且可逆的策略使用 switchback，预先定义切换周期、清洗期、季节和同期事件。
- 比较不同市场的触达饱和度，估计直接效应、溢出效应和系统净效应；不能只报告被触达用户结果。
- 无法获得足够独立簇、稳定周期或可接受污染时，停止因果宣称，改做受限试点和描述性监控。

## 4. 判断规则

### 4.1 数据是否足以回答

- 有事件顺序、统一窗口和匿名主体，才能做可靠漏斗。
- 有统一进入时点和后续行为，才能做 Cohort。
- 有结果金额、退款和成本，才能做利润口径 LTV/ROI。
- 有成熟标签和时间外验证，才能报告预测表现。
- 有合格反事实，才能报告增量和因果。
- 只有聚合累计值时，不还原用户路径、月度留存或个体模型。

### 4.2 模型是否值得上线

同时满足：

1. 模型结果对应明确动作、容量和负责人。
2. 相对于简单规则有可验证的业务净收益，而不只是离线指标更高。
3. 训练、验证和时间外样本符合实际使用时点。
4. 阈值由收益、成本、误伤和产能决定。
5. 可解释到足以审计，且有人工复核和申诉路径。
6. 线上实验、漂移监控、回滚和下线条件已定义。

否则保留为离线研究，不进入自动决策。

### 4.3 数据系统是否值得建设

至少有一个高频、高价值决策能说明：当前损失、数据缺口、使用者、动作、节省或新增价值、实施依赖和维护责任。若只是“想做精细化”或“同行都有 CDP”，先做最小数据集和人工流程验证。

## 5. 策略与实施

### 5.1 最小数据产品卡

| 字段 | 内容 |
|---|---|
| 决策用户 | 谁使用数据做什么决策 |
| 目标对象 | 用户/账户/企业/订单等 |
| 触发与时效 | 何时需要结果，允许多大延迟 |
| 输入 | 必需事件、属性、成本和来源 |
| 规则/模型 | 计算逻辑、版本和阈值依据 |
| 输出动作 | 人群、渠道、内容和退出规则 |
| 验证 | 基线、实验、主要和护栏指标 |
| 治理 | 权限、保留、审计、负责人和下线 |

### 5.2 分阶段建设

1. 统一一个决策的实体、事件、口径和历史回补。
2. 建指标字典与质量看板，先让结果可复现。
3. 用规则或人工流程跑通动作和反馈闭环。
4. 只在规模、复杂度或时效需要时引入 CRM/CDP/自动化。
5. 只在简单规则不足且标签成熟时建模。
6. 通过线上实验验证净收益，再逐步放量。

### 5.3 数据与模型上线清单

```text
实体与 OneID 规则：
事件、属性与版本：
指标字典与成熟日期：
质量测试与告警：
权限、保留和删除：
模型卡（如适用）：
实验与反事实：
线上阈值和产能：
监控、回滚和下线：
负责人和审查日期：
```

## 6. 指标

### 6.1 数据基础指标

- 身份映射覆盖、冲突、拆分、误合并和撤销率。
- 关键事件覆盖、重复、缺失、迟到、回补和异常分布。
- 跨系统指标差异、数据延迟、管道失败和版本影响范围。
- 标签覆盖、准确、一致、时效、使用和无动作标签占比。
- 权限异常、未授权访问、过期数据和删除请求完成情况。

### 6.2 模型指标

- 区分能力：按任务选择 AUC、精确率、召回率、排序或其他合适指标。
- 校准：预测概率是否与实际发生率一致。
- 业务价值：相对规则/基线的增量结果、净收益和单位干预成本。
- 稳定性：特征、预测、标签、分群和结果的时间漂移。
- 公平与风险：关键合法人群的误伤、遗漏、申诉和人工推翻。

增量/uplift 任务增加：随机干预数据覆盖、各处理组样本、分层增量曲线、AUUC/Qini 或等价排序指标、策略价值、净收益和异质性不确定性。指标名称本身不构成上线依据；必须与“不干预、简单规则或现行策略”在可执行容量下比较。

生存/时间事件任务增加：删失比例、时间依赖区分、各时间点校准、风险分层稳定性和业务机会窗内净收益。不得只报一个全局准确率。

离线指标不等于业务效果。报告必须包含验证窗口、样本、基线、阈值、置信区间或不确定性及失效条件。

### 6.3 测量指标

- 实验分流与样本比例异常、交叉污染和失访。
- 主要、诊断和护栏指标的成熟度与缺失。
- 归因覆盖、重复触点、自然基线和退款回冲。
- 增量效果、完整成本、贡献毛利和长期质量。
- 簇随机、switchback 或饱和度实验的簇数、污染、溢出、清洗期和双侧系统效应。

## 7. 护栏

- 数据采集遵循目的限定和最小必要，提供访问、修改、删除、撤回和申诉机制。
- 直接标识不进入普通分析与公开交付；敏感属性不用于歧视性运营。
- OneID、标签、特征、模型和归因规则必须有版本、负责人、审计和回滚。
- 高风险权益、拒绝服务或价格决策不能仅由模型自动执行。
- 不输出未经验证的个体结论，不把预测概率写成事实标签。
- 不引用无来源的模型准确率、行业阈值、工具效果或投资回报。
- 工具选型保持数据可导出、接口可替换和退出能力，避免不可逆供应商锁定。

## 8. 停止条件

出现以下任一情况，停止分析、自动动作或模型放量：

- 身份误合并、事件断流、重复或口径变化足以改变结论。
- 标签未成熟、结果泄漏、样本选择或时间穿越使模型验证无效。
- 实验分流异常、跨组污染、同期重大变更或结果窗口尚未成熟。
- 线上效果相对简单规则无净收益，或边际成本超过批准上限。
- 漂移、误伤、投诉、安全或隐私风险突破预设护栏。
- 数据来源、处理过程或模型版本无法追溯和复现。
- 系统无法暂停、回滚、删除或响应用户权利请求。

停止后先保留原始证据和版本，定位影响范围；不能静默修改历史数据后继续报告。

## 9. 输出契约

数据、模型或测量任务默认输出：

1. 决策问题、可回答范围和结论等级。
2. 实体—身份—事件—指标关系图或表。
3. OneID、事件字典和指标字典的最小版本。
4. 数据源、质量缺口、成熟日期和修复优先级。
5. CRM/CDP/仓库/自动化职责与最小建设方案。
6. 规则或模型选择、模型卡和不上模型的备选方案。
7. 归因、实验或准实验方案及因果边界。
8. 上线监控、护栏、回滚和停止条件。
9. 7 天补数/验证动作与 30 天基础建设清单。
