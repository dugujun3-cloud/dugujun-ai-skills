# 框架：从陪聊到能交

提炼自运营 AI 认知实践（聊天式用法 vs 交付式用法），供诊断时对照，不向用户原文朗读。

## 1. 默认错归因

常见反应：模型不够聪明 → 换更强的。

更常见的真实结构：

- 聊天式 AI 默认陪聊
- 用户丢需求 → 回一版「像样的东西」
- 运营要的是能交差：方案能落地、表能用、结论能推到动作
- 对话框多是**半成品**：看着省了开头，费时间的是后半段整理
- 它吐内容，你拼装和背锅；勤快解决不了，因为活被拆成两截

## 2. 三关机制

### 2.1 半成品要你收尾

- 过程热闹（方案也写、图也出、数也拆），效率几乎不动
- 半成品拖着不办会越攒越多，压力仍在人身上
- 聊天框能吐像样文字，很难替你把运营活交出去

### 2.2 聊越多越亏时间

- 模型一般时，同一套坑更烦：改一版口径飘，再纠正换一种错
- 时间耗在改错链上，不如自己做收工早
- 继续聊常常不是因为顺，而是已经投了这么久，停了可惜
- 模型选错要命；模型选对了却只闲聊，交付照样落在自己身上
- 文案或许能聊顺，方案往往还是半截

### 2.3 换了等于白换

- 别先盯哪个应用更好看
- 先看：模型能力是否第一梯队；是否离开纯聊天
- 模型再强，只挂在对话框里：便宜省的是零花钱，省不下夜晚
- 入口换了、干活方式没换 = 白换
- 门槛不在会不会点新软件，在有没有把活从陪聊推进到能交

## 3. 两轴验收题（必须会问）

对任何「AI 工具 / 工作流」只逼问：

1. 能不能**记住这活的规矩**？
2. 能不能**改到能交差为止**？
3. 还是每一步都得用户**粘贴、验收、拼装**？

判定：

| 状态 | 含义 |
|------|------|
| 干活 | 记得规矩 + 改到能交 |
| 陪聊 | 每一步靠人拼 |
| 混用 | 局部能交（如短文案），关键交付仍半截 |

## 4. 钱与时间

- API/订阅看着不贵，半截工程一返工，时间和钱一起涨
- 大半夜还在改表：多半不是哪个模型更贵更便宜，是用法停在聊天框

## 5. 改造优先级（处方排序）

1. 先定义「能交」长什么样（交付物 + 验收线）
2. 再外置规矩（可复用规则/Skill/固定上下文）
3. 再串连续步骤（少粘贴）
4. 设停损（纠正轮次/口径飘）
5. 最后才动工具：升级模型或换到能连续干活的工具链，并验证交付

## 6. 与「先画流程」的衔接

若用户连日常流程都画不清：先让其标出最吃时间的瓶颈环节，再把 AI 插在瓶颈上做「能交」试验（参考：运营学 AI 第一步应是认识自己的系统，不是先找工具试用）。

## 7. 工具举例（仅作量级参考，非排行）

- **模型性价比轴**：按量可用、能力价格站得住的一类（如 DeepSeek 类）
- **离开纯聊天轴**：复杂任务、连续步骤更能扛的一类（如 Claude Code、Codex 类）

举例必须回到两轴验收题，禁止做成安利清单。
